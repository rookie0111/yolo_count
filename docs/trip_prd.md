# 途灵 TripMind PRD

## AI 速读卡

- **产品一句话**：输入目的地和预算，AI 自动生成含景点、住宿、天气预警的动态行程计划。
- **核心循环**：设定需求 → AI 生成日计划 → 手动调优 → 天气变化自动重新规划 → 出行中实时调整
- **硬约束**：行程方案必须可编辑；天气变动必须触发主动重规划通知；预算不得超限除非用户确认
- **推荐默认**：Web 优先，移动端适配；本地优先存储，不强制登录
- **发挥空间**：地图可视化细节、行程卡片交互动效、语音输入目的地、分享行程长图样式
- **P0 验收**：输入"北京 3 天 2000 元" → 生成含景点+酒店+每日预算的行程 → 模拟天气变化 → 系统提示并给出替代方案
- **最容易翻车**：大模型输出幻觉（虚构酒店/票价/开放时间）→ 需联网检索验证关键事实
- **超预期机会**：出发前生成美图分享卡；行程结束后自动拼贴旅行回忆长图

## 第一章：产品概述

途灵 TripMind 是一款 **AI 旅行规划助手**，让 **自由行旅行者** 能够**输入目的地、天数、预算后一键获得完整可执行行程**，而无需**手动在攻略、订票网站、地图、天气 App 之间来回切换拼接**。

### 1.1 差异化对比表

| 功能 | 携程/飞猪 | 小红书攻略 | 途灵 TripMind |
|---|---|---|---|
| 景点推荐 | 按销量排序，偏商业 | 种草帖，时效性参差 | AI 根据偏好+预算+天气动态推荐，标注推理来源 |
| 行程拼接 | 用户手动添加，无约束校核 | 纯文本，无结构 | 自动生成日计划，地图上验证路线可行性，通勤时间计算 |
| 天气响应 | 仅在首页展示天气预报 | 无集成 | 行程中天气突变自动重新规划当日方案，推送替代建议 |
| 预算管控 | 预订后可见总价 | 无 | 生成时即出总预算，行程中实际支出录入，超限预警 |
| 可编辑性 | 无法批量调整 | 不可执行 | 每条建议可删除/替换/重新生成，拖动调序 |
| 行程导出 | PDF 订单确认 | 截图 | 结构化 JSON + 分享长图 + 日历订阅 |

### 1.2 三类用户画像

| 角色 | 核心目标 | 最大不满 | 切换触发功能 |
|---|---|---|---|
| 小张 — 首次自由行的学生 | 花最少的钱玩到最值的内容 | 攻略太多太杂，不知道信谁的 | 输入预算一键出方案，心中不慌 |
| 阿琳 — 带娃出行的年轻妈妈 | 行程安全、节奏舒适、突发情况有预案 | 下雨天原定户外行程完全作废，临时找室内项目手忙脚乱 | 天气变动自动切换到室内备选方案 |
| 老刘 — 每年出行 3-4 次的自由行老手 | 高效规划，不愿在工具间来回切换 | 机票酒店攻略地图天气预报各自一个 App，信息分散 | 一个入口搞定全流程，还能手动精调每个细节 |

### 1.3 可行性边界

| 在范围内（及原因） | 明确排除在外（及原因） |
|---|---|
| AI 生成日程 + 路线 + 预算方案 | 直接在此产品内完成酒店/机票/门票支付 — 涉及支付牌照、供应链对接，v1 仅做推荐+跳转链接 |
| 天气接入并触发动态重规划 | 实时路况导航 — 属于地图导航类产品核心能力，超出范围 |
| 用户编辑、替换、重新生成行程项 | 多人协作规划 — v1 仅单用户，多人协作需要完整账号体系和同步机制 |
| 行程 JSON 导出、分享长图、日历订阅 | 离线地图下载 — 需要大量地图瓦片存储，v1 在线使用 |
| 大模型生成 + 联网检索事实核验 | 用户生成内容（UGC 攻略社区）— 属于内容平台，非本产品定位 |

### 1.4 约束分层

| 硬约束 | 推荐默认 | 发挥空间 |
|---|---|---|
| 行程总预算不得超限，除非用户主动确认超限弹窗 | Web 应用，响应式适配移动端 | 路线地图的渲染风格、标记 icon 设计 |
| 天气发生重大变化（降雨概率>60%、温度骤变>8°C）必须主动推送通知并附替代方案 | OpenAI GPT-4o 或兼容接口生成行程 | 行程卡片的展开/折叠动效 |
| 大模型输出的景点、酒店、票价必须标注"AI 生成"或"已验证" | localStorage 为主，Chrome 本地存储无需登录 | 语音输入目的地和偏好 |
| 行程方案 100% 可编辑（增删改拖拽） | 先支持中国大陆城市，再扩展海外 | 分享长图的排版模板设计 |
| 用户隐私数据不出本地，API 请求仅发送脱敏后的规划参数 | 后端用轻量 Python/FastAPI 处理天气查询+联网检索 | 黑暗模式下地图配色 |

### 2.3 布局理由

旅行规划是"宏观看日程节奏 + 微观看单品决策"的任务。顶部需求输入区保持可回溯修改；主体时间线纵向结构符合"一天一天看"的认知顺序，日标签栏实现快速切换；预算仪表盘始终可见，防止偏离预算；天气预警作为全局浮层，确保优先级最高的信息不被埋没。

| 校验失败 | 必填项为空或预算为 0 | 问题字段红色边框 + 下方错误提示文案 | 修正后字段失去焦点 |

| 生成完成 | 后端返回结果 | 页面滚动至行程面板，输入区折叠至顶部摘要条 | 用户再次修改输入并生成 |

```

```

#### e) 待决问题

1. **多目的地连程**（如"上海→杭州→苏州 7 天"）：v1 仅支持单目的地，多目的地涉及城市间交通衔接，复杂度显著增加。标记为 P2。
2. **偏好标签的自定义程度**：是固定 6-8 个标签还是允许自由文本输入？推荐默认固定标签 + "其他"自由文本。

#### e) 待决问题

1. **酒店预订与实际价格偏差**：AI 参考价可能与实际预订价格存在 20-40% 偏差。建议在酒店项悬停时提示"参考价，实际以平台为准"。
2. **通勤时间的准确性**：地图 API 只能返回当前时刻的预估时间，未来时段的通勤可能因出行高峰而变化。v1 默认用该时段平均值 + 缓冲 20%。

## 第四章：超越竞品的差异化功能

### 4.1 天气驱动的主动行程重规划

#### 竞品为何没有这个功能

主流旅游平台（携程、飞猪、马蜂窝）的核心收入来自交易佣金，其产品重点放在"预订转化"上，天气仅作为信息展示模块存在，不做行程层面的联动。小红书等攻略平台是 UGC 内容，根本不具备结构化行程的实时调整能力。Google Trips 曾尝试但已于 2019 年关闭，原因在于其产品定位偏向"信息收纳盒"而非"智能规划代理"。

#### 本产品如何实现

1. 行程生成时为每一项添加 `indoor` / `outdoor` 标签（大模型自动判断）
2. 接入开放天气 API（和风天气 / OpenWeatherMap），行程日期范围内定时轮询
3. 风险引擎根据降雨概率、温差、极端天气预警计算影响评分
4. 仅当户外行程项受高风险影响时，触发大模型重新生成当日室内备选方案（复用已填偏好）
5. 通知用户而非静默替换，保持用户主导权

#### 交互流程

```
天气 API 返回降雨概率 85%
    |
    v
风险引擎标记：户外项 ×3，受影响
    |
    v
调用大模型："北京 6月21日 降雨概率 85%，请推荐 3-4 个室内替代行程项，
         要求与用户偏好'城市观光'一致，且单日总价不超过 ¥667"
    |
    v
生成替代方案卡片，推送到前端
    |
    v
用户查看 → 应用建议 → 当日行程项全部替换为室内方案
         → 自行调整 → 仅标注影响，用户手动一个个替换
         → 保持原计划 → 忽略通知，24h 内不再推送
```

#### 风险与应对

| 风险 | 应对 |
|---|---|
| 天气预报不准，白调整了 | 仅替换为"备选方案"，在用户侧仍可一键恢复原计划，不强制 |
| 大模型推荐了不存在的室内景点 | 每一项必须附"已验证"或"AI 生成"标记；联网检索结果标记为"已验证" |
| 室内方案不够吸引人 | 展示时附评分和用户评价摘要（来自第三方 API），用户可自行决定 |

```jsonc
    "day_sample": {                             // 单日行程对象

        "item_sample": {                        // 单个行程项
          "id": "item_001",                    // 行程项唯一 ID
          "time_start": "09:00",                // 开始时间，HH:MM 格式
          "time_end": "12:00",                  // 结束时间，HH:MM 格式
          "type": "attraction",                 // 类型: attraction | food | hotel | transport | custom
          "name": "故宫博物院",                  // 名称，必填

          "lat": 39.9163,                      // 纬度，用于地图
          "lng": 116.3972,                     // 经度
          "alternatives": "item_005, item_012"  // AI 推荐的替代项 ID，逗号分隔，可选
        }
      },
      "day_budget_planned": 462,                // 当日规划预算（元）
      "day_budget_spent": 0                     // 当日实际支出（元），默认值: 0
    }
  },
  "budget_summary": {                           // 预算汇总（派生数据，不从存储读取）
    "total_planned": 1840,                      // 规划总支出
    "total_spent": 0,                           // 实际总支出
    "by_category": {                            // 分类汇总
      "attraction": 422,
      "food": 480,
      "hotel": 560,
      "transport": 278,
      "other": 100
    }
  }
}
```

### 设计决策

- **weather 快照而非实时引用**：行程中的天气数据是生成时或最近刷新时的快照，避免 AI 重新解读历史行程时引用已失效的天气。
- **source + verified 双字段**：`source` 记录来源类别（AI 生成/验证/用户添加），`verified` 标记是否经过联网检索核实，让前端可以差异化展示可信度标签。
- **预算派生而非存储**：预算汇总从 items 集合中的 price 字段实时计算，不单独持久化，避免数据不一致。
- **day_budget_spent**：出行中用户手动录入实际消费，用于对比规划与实际的偏差。

### 6.2 依赖表

| 库名 | 用途 | 为何优于替代方案 | 大致包体积 |
|---|---|---|---|
| React 18 | 前端渲染 | 生态最大，AI 编程助手最熟悉，组件库丰富 | ~40KB gzipped |
| Zustand | 状态管理 | 比 Redux 轻量 90%，适合单页复杂状态但不需要中间件生态 | ~1KB gzipped |
| Leaflet | 地图展示 | 开源免费，无 API Key 限制，比 Google Maps 更适合轻量展示 | ~40KB gzipped |
| FastAPI | 后端 API | 异步原生支持，自动生成 OpenAPI 文档，AI 友好 | 未知 |
| LangChain | LLM 编排 | 标准化的对话 + 工具调用链，支持联网检索 plugin | 未知 |
| Tavily Search | 联网事实检索 | 专为 AI Agent 设计，返回结构化结果，优于通用搜索引擎 | N/A (API) |
| 和风天气 API | 天气数据 | 中国大陆覆盖最好，免费额度充足 | N/A (API) |
| SQLite | 开发环境数据库 | 零配置，单文件，无需 Docker | ~700KB |

### 6.3 最大架构风险

**大模型幻觉导致行程信息不可信。** 如果行程中推荐的景点门票价格比实际高 50%，或推荐了正在整修的景点，用户会失去信任。

应对策略：
1. 每条 AI 生成的行程项在返回前端前，调用 Tavily 联网检索验证名称、营业状态、参考票价
2. 验证成功 → 标记 `verified: true`
3. 验证失败或在时限内未找到结果 → 保留 `verified: false`，前端显示"AI 生成，请手动核实"
4. 允许用户在行前一键"重新验证全部"

### 6.4 可替换技术原则

前端框架推荐 React，如果项目已有 Vue/Svelte 可沿用；地图库推荐 Leaflet，如果已有 MapLibre/Google Maps 可沿用。**不可变的是**：行程时间线交互（拖拽、替换、预算联动）、天气风险三层评估逻辑、行程数据 JSON schema 中的字段语义。大模型推荐 GPT-4o，如果已有 Claude/DeepSeek/通义千问且效果可接受，可替换；不可变的是必须支持 function calling 用于联网检索触发。

## 第十一章：开发者交接说明

### a) 实现顺序建议

1. **先做行程时间线渲染（纯前端，无后端依赖）**— 用 mock JSON 数据验证时间线交互（展开、折叠、删除、替换），确定数据模型稳定后，后续所有模块以此为基准。这是产品体验的核心。
2. **再做输入面板 + 后端生成 API**— FastAPI 端点接入 LangChain + 大模型，返回行程 JSON。验证生成→渲染的完整闭环。
3. **最后做天气模块**— 因为天气需要定时轮询和风险引擎，在行程数据模型稳定后再接入，避免数据字段反复变更。

### b) 最可能导致返工的三个决策

| 决策 | 安全默认 | 转向信号 |
|---|---|---|
| 行程数据结构中价格是人均还是总额 | 总额，items 集合中每个对象的 price 字段表示该行程项的总费用（人数已在 `trip.travelers` 中） | 如果用户反馈多人出行价格分摊不直观，可增加 `price_per_person` 字段 |
| 大模型一次返回全部天数 vs 逐天调用 | 一次返回全部天数。虽然单次调用体量大（~2000 token 输出），但避免了多轮对话中的上下文漂移 | 如果 7 天以上的长行程出现质量下降（后几天空洞），改为先总体框架再逐天细化 |
| 天气查询在客户端直连 vs 通过后端代理 | 后端代理。保护和风天气 API Key 不外泄，同时可加入缓存层减少调用量 | 如果后端延迟成为瓶颈且用户量小，可暂时客户端直连 |

### c) 哪里要严格，哪里可以灵活

| 区域 | 级别 | 原因 |
|---|---|---|
| 行程数据模型 JSON schema | 硬约束 | 前端渲染、导出、分享、持久化全部依赖此 schema，任何字段增删改须同步所有模块 |
| 天气风险评估三级（low/medium/high） | 硬约束 | 三级阈值对应不同的 UI 反馈强度，不可简化为两级 |
| budget 计算逻辑 | 硬约束 | 必须从 items 求和，不能缓存可能过期的数字 |
| 用户隐私（行程数据不出本地） | 硬约束 | API 仅发送匿名参数 |
| 前端 UI 框架和组件库 | 建议 | React/Vue/Svelte 均可，推荐 React |
| 大模型选择 | 建议 | GPT-4o 最佳，但支持切换为任何兼容 OpenAI chat/completions 接口的模型 |
| UI 动效和视觉风格 | 发挥空间 | 时间线展开动画、卡片阴影、地图标记样式均可自由发挥 |
| 分享长图排版 | 发挥空间 | Canvas 渲染布局允许创意设计，核心要求：包含日期+行程概览文字 |

### d) 已知的未知项

1. **此处未解决：大模型生成的行程质量是否满足用户预期** — 取决于模型能力和 prompt 工程，v1 需要经过 30+ 个真实城市和预算组合的人工评测。如果差评率 > 30%，需要加入 few-shot 示例或微调。
2. **此处未解决：国内城市地图数据是否免费** — Leaflet 底图需要选用合适的 tile provider；高德/百度地图瓦片可能涉及 Licensing 和配额问题。推荐先用 OpenStreetMap 瓦片 + 高德地理编码 API 做正向查询。
3. **此处未解决：在微信内置浏览器中下载 ZIP 是否可用** — 微信浏览器对文件下载支持不完整，可能需要在分享长图之外增加"复制链接"的降级方案。

### e) 验收剧本

**验收剧本 1：** 在 Chrome 桌面端打开应用，在输入面板填写"北京"、3 天、预算 2000，点击"生成我的行程"，应在 15 秒内看到 3 天的时间线，每天至少包含 2 个景点 + 1 餐饮 + 1 住宿。用 Chrome DevTools → Performance 记录从点击到渲染的完整时间。

**验收剧本 2：** 在已生成的行程中，点击某行程项的"× 删除"，应看到弹窗确认，确认后该项消失，预算仪表盘数字即时更新（减掉该项价格）。打开 Chrome DevTools → Console，观察无 JavaScript 异常。

**验收剧本 3：** 模拟天气变化（修改天气 API mock 返回，将第 2 天降雨概率改为 85%），刷新后应在第 2 天日标签旁看到 🔴 标记，顶部出现黄色浮层，浮层中列出受影响的户外行程项和室内替代建议。点击"应用建议方案"后，第 2 天时间线应全部更新为室内方案。

**验收剧本 4：** 导出 3 天行程的 JSON 文件，用 `python3 -m json.tool` 验证 JSON 格式正确，用 `scripts/lint_prd.py`（本 skill 自带脚本）检查字段完整性。重新导入 JSON 应完整还原行程。

**验收剧本 5：** 在 iPhone 14（Safari）上打开应用，生成行程后应看到单栏布局，时间线卡片可触摸滑动，预算仪表盘在底部固定可见，不遮挡内容。用 Safari 响应式设计模式验证，任意宽度 >= 375px 下不应出现水平滚动条。
