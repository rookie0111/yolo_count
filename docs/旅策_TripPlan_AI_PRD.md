# 旅策（TripPlan AI） PRD

## AI 速读卡

- **产品一句话**：旅策是一款 AI 行程规划助手，让自由行旅行者输入目的地与偏好后自动生成景点推荐、预算明细、住宿方案和每日行程，并依据实时天气动态调整，无需手动在多个 App 之间来回切换。
- **核心循环**：输入偏好 → AI 生成多方案 → 逐日调整 → 天气触发重排 → 一键导出
- **目标平台**：Web（PWA）+ 移动端 H5（微信内嵌），MVP 优先 PWA 单页应用
- **硬约束**：用户数据本地优先；天气 API 必须实时拉取不可缓存超过 30 分钟；预算计算不允许遗漏任何明线条目（住宿/交通/门票/餐饮）；动态重排必须保留用户已确认的不可变项
- **推荐默认**：React + TypeScript，IndexedDB 本地持久化，天气用 Open-Meteo（免费无密钥），地图用 Leaflet（开源），AI 用通义千问 API
- **发挥空间**：行程卡片动画、天气切换时的过渡动效、智能打包清单、分享卡片视觉风格、离线包压缩策略
- **P0 验收**：输入城市+天数+预算 → 生成含景点、住宿、每日行程的完整方案 → 模拟天气变化 → 行程自动重排 → 导出为 PDF
- **最容易翻车**：天气 API 调用失败时整个重排链路静默崩溃；预算估算与实际价格偏差过大导致用户信任崩塌
- **超预期机会**：行程冲突检测弹窗（两个景点之间通勤时间不够）、"雨天备选方案"一键切换、行程分享生成带地图的微信卡片

## 第一章：产品概述

旅策 是一款 AI 驱动的自由行规划助手，让 计划自由行但厌恶手动查攻略的旅行者 能够 输入一次偏好即可获得完整的、可调整的、天气自适应的行程方案，而无需 在攻略网站、地图 App、酒店平台、天气 App 和记账本之间反复复制粘贴。

### 1.1 差异化对比表

| 功能 | 竞品（穷游行程助手 / 携程AI / ChatGPT） | 本产品 | 实现方式 |
|---|---|---|---|
| 天气动态重排 | 穷游无天气联动；携程仅提示天气不重排行程；ChatGPT 需手动追问 | 天气变化自动触发重排，生成室内备选方案 | Open-Meteo 定时轮询 + 规则引擎匹配景点室内/室外标签 |
| 预算穿透式估算 | 穷游/携程仅显示机酒总价，不拆分明细；ChatGPT 给出笼统数字 | 逐项展开：机票、住宿×晚、每日餐饮、各景点门票、市内交通，汇总时标注置信区间 | 基于目的地城市的价格基线与用户偏好等级计算，每个条目标注估算置信度 |
| 矛盾检测 | 三者均无 | 自动检测：行程时间 vs 通勤距离冲突、预算 vs 方案超支、体力消耗 vs 连续爬山/徒步 | 约束求解 + 规则引擎，行程生成后运行检测阶段 |
| 离线行程包 | 穷游可离线查看但格式固定；携程需联网；ChatGPT 不支持 | 一键导出含地图、导航链接、中文地址、酒店预订单模板的离线 HTML+PDF 包 | Service Worker 缓存 + 客户端打包 |

### 1.2 三类用户画像

**画像 A：第一次自由行的预算敏感型年轻人**
- 角色：25 岁，月薪 12k，攒了 3 个月钱准备去日本 5 天
- 核心目标：在 8000 元总预算内完成大阪-京都行程
- 最大不满：查攻略时预算信息分散，订完机票发现住宿超预算
- 切换功能：预算穿透式估算——输入 "8000 元" 后看到每一项花多少钱、还剩多少钱

**画像 B：带父母出行的中年子女**
- 角色：38 岁，计划带父母去云南 7 天
- 核心目标：行程不能太累，住宿要干净安静，每天 3 个景点以内
- 最大不满：攻略推荐的 "必去" 景点老人根本走不动
- 切换功能：体力强度标签 + 天气动态将暴晒景点替换为室内

**画像 C：频繁出差顺带旅游的商务人士**
- 角色：32 岁，每月出差 2-3 次，每次有 1-2 天空闲
- 核心目标：快速生成半天到一天的极紧凑行程
- 最大不满：所有工具都按 "度假" 思路设计，没有 "我只有 6 小时" 的模式
- 切换功能：基于酒店定位的半日快游模式，行程按步行可达排列

### 1.3 可行性边界

| 在范围内（及原因） | 明确排除在外（及原因） |
|---|---|
| 景点推荐基于 POI 数据库 + AI 排序 | 不在 MVP 中接入实时门票库存与购买（需与各平台签约） |
| 基于公开天气 API 的动态调整 | 不做灾害预警推送（需要法律合规审核） |
| 预算估算的置信区间标注 | 不保证价格与实际预订完全一致（数据源为估算基线） |
| Web PWA 支持离线查看已保存行程 | 不做原生 iOS/Android App（MVP 阶段资源不足） |
| 中文城市与景点数据 | 不做多语言（P0 仅中文） |
| 单人/多人出行方案生成 | 不做团队实时协作编辑（P2） |
| 分享链接 7 天有效 | 不提供永久公开行程社区（P3） |

### 1.4 约束分层

| 硬约束 | 推荐默认 | 发挥空间 |
|---|---|---|
| 用户行程数据默认仅存储于浏览器 IndexedDB，不上传服务器 | 后端用 Node.js + SQLite，部署在单台 2C4G VPS | 卡片展开/收起动画可使用 Spring 物理动画增强质感 |
| 天气数据拉取间隔不超过 30 分钟，且必须在 UI 标明数据时间 | 天气 API 用 Open-Meteo（免费，无需 API Key） | 加载骨架屏设计风格、Empty State 插画风格 |
| 预算计算必须逐项列出（住宿/交通/门票/餐饮/其他），不可合并 | 前端用 React 18 + TypeScript + Tailwind CSS | 地图标记点聚类算法可选 Supercluster 或自定义 |
| 动态重排必须保留用户已标记为 "已确认" 的条目 | AI API 优先通义千问，备选 DeepSeek | 分享页面的 og:image 动态生成（带行程摘要的地图截图） |
| 导出文件不能包含外部 CDN 依赖，必须离线可打开 | 导出用 jsPDF + JSZip 在客户端完成 | — |

#### c) 状态清单

| 名称 | 触发条件 | 视觉标识 | 退出条件 |
|---|---|---|---|
| 空闲 | 页面初始加载 | 空表单，所有字段默认值 | 用户开始输入 |
| 输入中 | 用户聚焦任一表单字段 | 字段高亮，城市搜索展示下拉 | 失焦或提交 |
| 校验失败 | 必填字段为空或日期范围无效 | 红色边框 + 字段下方错误提示文案 | 修正并重新校验 |
| 提交中 | 点击 "开始生成" | 按钮置灰 + 旋转加载图标 + "正在生成行程..." 文案 | API 返回结果或超时 |
| 生成成功 | API 返回有效行程数据 | Toast "行程已生成" + 自动跳转 | 页面跳转完成 |
| 生成失败 | API 超时或返回错误 | Toast + 错误详情 + "重试"按钮 | 用户点击重试或取消 |
| 部分成功 | 生成完成但某些天景点不足 | 行程页标记 "⚠ 第3天景点较少，可手动添加" | 用户手动补充或忽略 |
| 离线降级 | 网络断开且无缓存行程 | 提示 "需要网络以生成新行程；已有行程可离线查看" | 网络恢复 |

#### d) 依赖关系

```
读取：城市 POI 数据库（本地 JSON）、用户偏好标签预设（本地 JSON）
写入：新行程对象 → IndexedDB.行程表（trip_id 为主键）
     新行程元数据 → IndexedDB.元数据表
调用：AI API（通义千问 / 备选 DeepSeek）
     天气 API（Open-Meteo）—— 生成时拉取预测天气以嵌入行程
```

#### e) 待决问题

1. **此处未解决**：自定义城市（POI 库未覆盖的小众目的地）是否需要依赖 AI 自主生成全部内容？当前默认：AI 生成 + 标注 "信息可能不完整，建议到目的地后确认"。
2. **此处未解决**：用户输入的出行日期距离当前 >14 天时，天气 API 仅能返回气候平均值而非具体预报。当前默认：14 天外显示 "气候参考" 而非 "天气预报"，并在出发前 7 天推送提醒（如用户同意通知权限）。
3. 无。

## 第四章：超越竞品的差异化功能

### 第 4.1 节 天气自适应行程动态重排

1. **竞品为何没有这个功能**：穷游/携程的行程模块是静态数据编辑器，其技术架构将 "行程" 存储为纯文本列表，没有景点属性标签（室内/室外/半室内），也没有事件驱动的重排引擎。ChatGPT 虽然能理解天气影响，但无法在用户不主动追问的情况下监控天气变化并触发重排——它缺少后台轮询和推送机制。
2. **本产品如何实现**：每个景点在 POI 数据库中标注 `indoor`（室内）、`outdoor`（室外）、`semi`（半室内）。后台 Service Worker 每 30 分钟拉取 Open-Meteo 天气数据，比对未来 48 小时不利天气（降雨概率 >60%、风速 >30km/h、温度 >38°C 或 <0°C），匹配受影响天数和室外景点，生成替换候选列表（同区域、同类型、室内标签），推送给用户确认。用户可选择一键替换、逐项确认或保持原行程。
3. **交互流程**：
```
Service Worker 定时拉取天气 API
    |
    +-- 新天气数据到达 → 与缓存对比 → 无变化 → 静默
    |
    +-- 天气变化（如晴天→雨天）
         |
         v
    匹配受影响行程 → 生成替换方案 → 更新 IndexedDB 天气缓存
         |
         v
    用户打开页面 / 已在前台 → 展示天气预警 banner
         |
         v
    用户操作 → 行程更新 → 同步到时间线视图
```
4. **风险与应对**：天气预测不准确（预报有雨实际没下，导致用户错过了户外景点）——应对：替换后的景点卡片上显示 "因天气调整 ↑" 可撤销标签，用户可在出发前随时手动恢复原景点。天气 API 调用频率过高触发限流——应对：降级为 1 小时一次轮询，明示数据更新时间。

### 第 4.2 节 预算穿透式估算 + 矛盾检测

1. **竞品为何没有这个功能**：竞品要么只做预算（记账类 App），要么只做行程（攻略类 App），数据模型不相通。记账 App 不知道你那天要去哪个景点要花多少门票钱；行程 App 的 "总预算" 只是一个文本框而非计算字段。将两者打通需要行程数据结构中嵌入价格字段，且需要与预算模型实时联动——这需要系统性的数据建模工作，而非简单的 UI 拼接。
2. **本产品如何实现**：行程生成时，AI 在景点、住宿、餐饮节点中嵌入 `estimated_cost` 字段（含 `min`/`max`/`confidence` 三个子字段）。预算模块从前端聚合所有节点的成本区间，按类别分组展示。总预算为硬约束输入，实时对比。冲突检测规则：`sum(各项 min) > 总预算` 时触发超标警告，AI 生成削减建议。
3. **交互流程**：
```
行程生成 → 各节点附带 estimated_cost
    |
    v
预算模块聚合 → 展示分类饼图 + 明细列表
    |
    +-- 总和 ≤ 预算 × 0.9 → 绿色正常
    +-- 总和在 90%-100% → 黄色预警 "预算紧张，建议预留缓冲"
    +-- 总和 > 预算 → 红色超标 + AI 削减建议弹窗
         |
         v
    用户调整某项 → 实时更新进度条
```
4. **风险与应对**：估算与实际价格偏差过大导致用户信任崩塌——应对：每项价格旁边标注 "预估" 标签 + 置信度指示（高/中/低），在 P2 版本中接入实时价格 API 替换估算。

### 第 4.3 节 一键离线行程包导出

1. **竞品为何没有这个功能**：穷游的离线功能依赖其自有 App 的本地存储，格式固定不可自定义。ChatGPT 的导出只是纯文本复制。携程行程不支持完全离线。原因在于：离线包需要将地图瓦片、导航数据、中文地址、酒店预订单模板、图片等全部打包为一个自包含文件，技术复杂度高（需处理跨域资源、图片 base64 编码、地图离线瓦片缓存等）。
2. **本产品如何实现**：导出时在客户端构建一个包含所有行程数据的 HTML 文件 + 地图 Leaflet 离线瓦片（预缓存目标城市 zoom 12-16 级别） + PDF 行程单。使用 Service Worker 缓存瓦片，JSZip 打包所有资源。HTML 页面内嵌完整的 CSS 和 JS，不依赖任何外部 CDN。
3. **交互流程**：
```
用户点击 [导出]
    |
    v
选择格式：□ HTML 离线包  □ PDF 行程单  □ 两者
    |
    v
客户端收集：行程 JSON + 地图瓦片(Base64) + 酒店信息 + 天气预报截图
    |
    v
JSZip 打包 → 生成 zip + 下载
    |
    v
HTML 离线包在任意浏览器打开：
    ├── 顶部：行程摘要 + 天气预报
    ├── 中间：逐日时间线（可折叠）
    ├── 底部：费用汇总表 + 酒店预订单模板（可打印）
    └── 侧边：离线地图（已缓存瓦片）
```
4. **风险与应对**：地图瓦片缓存量大（一个城市约 20-50MB）→ MVP 仅缓存 zoom 12-14 基础瓦片（约 5MB），标注 "需要更详细地图请在有网络环境下访问在线版"。导出时间过长（>30s）→ 显示进度条 "正在打包 45 个地图瓦片..."。

### 最大架构风险

**AI API 调用成本与延迟**：每次行程生成需调用 AI API（预估 ~2000 tokens 输出），单次耗时 5-15 秒，成本约 ¥0.05-0.10。如果用户频繁 "重新生成"，可能产生较高费用和等待时间。

应对策略：
- 生成结果缓存到 IndexedDB，相同参数（目的地+日期+偏好）的重复请求直接返回缓存
- 单用户 24 小时内最多免费生成 10 次，超过提示 "今日生成次数已达上限"（P1 接入付费）
- 预生成常见目的地+季节的模板行程，本地优先匹配，匹配不到才调用 AI

### 可替换技术原则

- 推荐 React + Zustand；如果项目已有 Vue 3 + Pinia，可用 Vue（行程数据结构不变）。
- 推荐 Tailwind CSS；如果项目已有 Ant Design 或 shadcn/ui，可沿用。不可变的是：响应式断点（320px / 768px / 1280px）和移动端优先的触摸交互区域（最小 44x44px）。
- 推荐 Open-Meteo 天气 API；备选和风天气 API（需注册，免费额度 1000 次/天）。不可变的是：天气数据 30 分钟过期规则和不利天气的判断阈值。
- 推荐通义千问；备选 DeepSeek、GPT-4o。不可变的是：AI 输出必须符合 JSON Schema 定义的行程结构，且必须在 prompt 中要求 `indoor_type` 字段。

| IndexedDB 写入失败（存储已满） | "设备存储空间不足，行程未能保存。请清理空间后重试。" | [重试保存] [导出备份再清理] |
| AI 返回格式不符合 JSON Schema | "行程生成异常，正在重新生成..." | 自动重试（最多 3 次），失败后降级为模板行程 |
| 导出打包失败（内存不足） | "导出过程出错，可能是地图数据过大。已为你生成不含地图的纯文本版本。" | [下载纯文本版] [重试完整版] |

### 7.5 加载状态

| 操作 | 加载类型 | 延迟阈值 |
|---|---|---|

| 导出打包 | 模态框 + 进度条（百分比 + 当前步骤） | 始终显示 |
| 页面切换 | 目标区域骨架屏 | > 300ms 显示 |

## 第十一章：开发者交接说明

你好，实现者。这份 PRD 定义了一个旅行 AI Agent 的完整产品规格。以下是构建时需要知道的关键信息。

### a) 实现顺序建议

1. **先搭建数据层**（IndexedDB Schema + Dexie.js 封装）—— 因为所有其他模块都依赖它。确保 trips 表和 pois 表的读写通过单元测试。
2. **再实现行程创建向导 + AI API 集成**—— 这是用户进入产品的第一触点，也是验证 AI 输出格式（JSON Schema）是否稳定的关键。先确保 AI 返回的 JSON 符合 `trip.schedule` 结构。
3. **接着实现时间线视图**—— 因为有了行程数据后需要展示它。这是一个纯前端模块，不依赖外部 API，可以独立开发和调试。
4. **然后实现天气动态重排引擎**—— 依赖时间线视图和行程数据，是核心差异化功能。需要通过 Service Worker 或 `setInterval` 实现后台轮询。
5. **预算仪表盘**—— 纯聚合计算模块，依赖行程数据中的 `estimated_cost` 字段。
6. **最后实现导出模块**—— 依赖以上全部模块的数据就绪。

P0 完成后，按 P1 → P2 → P3 的优先级推进，每个 tier 内部可以并行开发。

### b) 最可能导致返工的三个决策

1. **AI 输出格式不稳定**
   - 决策：用什么方式约束 AI 返回结构化 JSON？
   - **安全默认**：使用通义千问的 JSON Mode（`response_format={"type": "json_object"}`）+ 在 prompt 中给出完整的 JSON Schema 示例 + 客户端 Zod 校验 + 校验失败自动重试（最多 3 次）。
   - **改向信号**：如果连续 3 天重试率 > 20%，替换 prompt 策略或切换到 GPT-4o（JSON Mode 更稳定）。

2. **天气数据轮询策略**
   - 决策：Service Worker Periodic Background Sync 还是前端 setInterval？
   - **安全默认**：前端 `setInterval`（30 分钟间隔）+ 页面可见时立即拉取。PWA 的 Background Sync 在不同浏览器实现不一致（iOS Safari 不支持），不要作为唯一依赖。
   - **改向信号**：用户反馈 "打开页面天气数据总是旧的"，则补充页面 focus 事件触发拉取。

3. **离线地图瓦片缓存策略**
   - 决策：预缓存哪些 zoom 级别？缓存多少瓦片？
   - **安全默认**：MVP 仅缓存 zoom 12-13 的城市级瓦片（一个城市约 50-80 个 PNG 文件，总计约 2-3MB），用于行程概览。不做街道级详细地图缓存。
   - **改向信号**：用户反馈 "离线地图太模糊看不到街道"，则在 P2 增加 zoom 14-15 瓦片（但文件体积增至 15-30MB，需让用户选择）。

### c) 哪里要严格，哪里可以灵活

| 章节 | 约束类型 | 说明 |
|---|---|---|
| 第三章 3.2 时间线视图 | 约束 | 景点卡片的结构（时间、名称、indoor_type、estimated_cost、操作按钮）必须完全实现 |
| 第三章 3.4 天气重排引擎 | 约束 | 不利天气判断阈值（降雨概率>60%等）不可改变；替换逻辑的核心流程不可改变 |
| 第一章 1.4 硬约束 | 约束 | 预算必须逐项列出、行程本地存储、导出文件必须离线可用 |
| 第五章 数据模型 | 约束 | `trip.version`、`schedule[].items[].indoor_type`、`estimated_cost.confidence` 字段必须保留 |
| 第九章 P0 | 约束 | P0 的所有条目必须完成才能交付 |
| 第二章 布局 | 建议 | 移动/桌面断点可调整，面板宽度比例可调整，但双栏布局结构不变 |
| 第七章 快捷键 | 建议 | 可增减快捷键，但不应移除 `Ctrl+N`（新建）和 `Ctrl+E`（导出） |
| 第三章 3.1/3.6 UI 细节 | 发挥空间 | 表单样式、动画效果、酒店卡片展示布局可自由设计 |
| 第八章 导出格式 | 发挥空间 | 离线包的 HTML 视觉风格、PDF 排版样式可自由设计 |
| 第七章 7.1/7.2 | 发挥空间 | 可增加更多快捷键和右键菜单项 |

### d) 已知的未知项

1. **此处未解决**：是否需要用户账号系统和云端同步？当前默认：MVP 不需要。所有数据存储在浏览器 IndexedDB，无后端。如果用户强需求多设备同步，则需要增加账号系统 + 后端 API + 数据库。届时数据模型中的 `trip_id` 已预留扩展空间。
2. **此处未解决**：景点 POI 数据库的来源和规模。当前默认：内置 50 个热门目的地 × 每个 100-200 个景点（总计约 100KB JSON）的精选数据。未覆盖的目的地完全依赖 AI 生成。这个策略的覆盖率和质量需要在真实用户测试中验证。
3. **此处未解决**：AI API 费用由谁承担？当前默认：P0-P1 阶段由开发者提供 API Key 免费供用户使用（限额 10 次/天/设备），P2-P3 可考虑让用户填写自己的 API Key 或接入付费方案。
4. **此处未解决**：通勤时间矩阵的精确度。MVP 使用预设的近似时间表（如 "大阪城内景点间平均 15-30 分钟"），不与实时交通数据挂钩。真实精度可能在地铁停运、节假日、修路等情况下严重偏离。
